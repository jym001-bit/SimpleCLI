# 阶段十：Harness 效果诊断与首轮评测驱动优化

本轮结论：单段摘要加入按输入长度计算的软长度建议后，观察到保留上下文更短，但没有证明整体降本、提速或任务成功率提升。完整固定集的输入、输出 Token 和调用次数反而增加，不能将本轮写成整体优化成功。

## 当前版本与执行口径

- 保留全部既有工作区修改；没有 Git 回滚、清理、Docker 或大型 Benchmark。
- 实际使用现有 `tools/run-harness-live-eval.ps1` / `LiveHarnessMain`，顺序执行。原固定集 `benchmarks/harness-live/cases.json` 的 SHA256 未改变，仍为 `f58399cd59efadca5fbafeb6715f78b09dbc87e9dc47817185a23f3272cb5a28`。
- 模型标识始终为 `deepseek-v4-flash`，同一配置下 temperature=1、top_p=0.95、thinking=enabled、reasoning_effort=max。没有可固定的 seed，也没有固定供应商后台修订版本；缓存命中、生成的前置回复与网络耗时会波动。
- 原任务提示词、工具权限、验收规则、压缩触发阈值均未改变。唯一有意修改的模型提示词是生产摘要器内部的长度指导，不是评测任务文本。工具只允许 read_file，夹具位于 target。
- 新增 3 个独立诊断任务 D01～D03，先运行修改前批次再改生产代码，修改后使用相同文件复测，文件 SHA 见结果。没有修改失败用例的验收标准。
- 原固定集前后各 12 次；诊断集前后各 3 次；L08 修改后追加 1 次，共 31 次真实任务尝试，全部保留，不选最好一次。两个 D01 失败均保留。
- 代码版本与逐源文件 SHA 在 source-before.json / source-after.json。相比本轮开始，主源码变化只有真实摘要器及评测运行器，没有覆盖其他模块的既有修改。

## 为什么选择摘要请求

原集自动评分 12/12，不能据此证明没有瓶颈。基线 L08 需要 8 次模型调用，其中第 7 次是摘要：云端记录该请求 759 输入、1023 输出 Token，耗时 6059ms。应用记录压缩只将估算上下文从 3472 降至 3338，净减少 134。摘要正文 815 字符，消耗较高而后续保留上下文缩短有限。

诊断集检查目标与只读约束、待办状态、实际读取 alpha.txt / missing.txt 的结果，以及用户更新后的决定。修改前后 11 个要求原样保留的事实标记都存在，且 D02、D03 的严格 JSON 回答通过。完整集里的 L05 在本次基线没有额外调用；L06 较慢没有足够证据指向 Harness Deadline。因而本轮仅选择摘要的长度指导，不增加 Deadline、重试或新的 Runtime。

## 实际生产改动

`src/main/java/com/paicli/memory/ConversationHistoryCompactor.java` 的单输入片段摘要路径，向原请求追加约原文三分之一的建议字符数，最低 400、最高 8000；要求省略确认语和重复背景，优先保留目标、约束、未完成事项、精确代号和必要工具证据。必要信息允许超出建议，不硬截断响应。

真实路径是 Agent/Plan/SubAgent → AutoCompactionManager → ConversationHistoryCompactor → 模型请求 → 原四栏目与净 Token 减少检查 → 原历史重建。多片段摘要与合并、保留最近轮次、工具消息边界、失败保留原历史等行为未改变。对应单测检查模型超过软目标时也不会被截断，关键尾部事实及最近消息仍完整保留。

评测辅助改动：`LiveHarnessMain` 与现有脚本增加可选 CasesFile；为手动压缩记录前后估算 Token 和摘要事实标记。原入口和 12 例默认行为保留。辅助字段本身不算 Harness 优化成果。

## 失败、评测盲点与云端证据

- **D01 两批均失败**：JSON 的 goal/constraint 等值附加了解释，或 pending 附加了状态文字，与期望值不相等。四个要求保留的标记都在；现有提示词没有充分约定字段只能含代号，无法据此断言是压缩丢失。保留严格失败，不修改题目或断言凑通过。
- **L05 修改后有顺序问题**：本地序列是成功读取 alpha.txt → 参数错误 → 再读 alpha.txt；基线是先错误 → 再读 alpha.txt。原评分器只检查出现过失败及目标路径，漏查“先故意错误再恢复”。原分数仍分别记录 12/12；两批一致增加“仅 L05 顺序审计”后为 12/12 与 11/12。这是补充审计，不冒充原固定集分数，也不代表已全面人工审查所有语义。
- **基线 L06 云端缺失**：本地 3 次模型、2 次工具，云端只有 2 次、1 次，稍后重查仍如此。模型 Usage 比较不通过。日志同时存在 `Failed to export 3 spans` / `HttpTimeoutException`，但业务任务成功。未重建或伪造缺失 Span，本轮没有修改遥测重试。
- 共读取历史 12 条及本轮 31 条 Trace。本轮 30 条能与本地调用数、Token Usage、父子关系和时间关系完整核对，另 1 条就是上述 L06；敏感 IO 检查未发现夹具正文或凭据上传。一次可选详情读取连接被重置，其未验证文件未纳入交付证据。
