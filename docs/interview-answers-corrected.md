# AI 应用开发面试题参考回答

## 第一大题：项目中遇到的最大挑战

### 派聪明 RAG 版本

我在派聪明 RAG 中遇到的最大挑战，是保证从文档解析、切片、召回、权限过滤到答案引用的整个过程都尽可能正确。把文档向量化存进 Elasticsearch，只是其中最简单的一步。

首先是文档切片。不同文件的结构差异很大，固定长度硬切很容易把一个完整语义截断。项目里采用了多级降级策略，优先按段落和句子边界切分，长句再用 HanLP 分词，仍然过长时才按字符切分。同时设置最小分片长度，并给相邻分片增加固定长度的语义重叠。PDF 还会保留页码和锚点，方便最终答案回溯来源。

其次是召回。项目同时执行 K 近邻（KNN）向量检索和关键词查询，再用 BM25 对候选结果重打分（rescore）和重排。为了提高候选覆盖率，会先召回 `topK × 30` 条候选，再截取最终的 topK。目前 30 倍召回和排序权重主要来自经验调参，下一步我会建设标准问答集和困难负样本（hard negative），通过 Recall@K、MRR、nDCG 等指标对不同参数进行评测。

最后是数据权限。私有知识库不能只在关键词检索中做权限过滤，KNN 检索也必须用相同的权限条件做前置过滤（pre-filter）。目前权限条件主要放在顶层关键词查询中，我还会把它同步加入 `knn.filter`，并在返回最终结果前再做一次权限校验，避免向量检索返回其他用户的私有文档。

这个项目让我意识到，做好 RAG 要让检索质量、权限正确性和答案可追溯性三件事同时成立，难度远超调用一次 Embedding API。当前项目已经完成文档解析、语义切片、混合检索、Agent 工具调用和引用回传，接下来我会重点补齐离线评测集和 KNN 权限过滤。

### PaiCLI Agent 版本

PaiCLI 中最大的挑战是长上下文管理。它远比“做一个摘要”复杂，既要压缩 Agent 实际发送给模型的消息历史，又要保证 ReAct 的工具调用协议不被破坏。

项目里一开始同时维护了两份数据，一份是 MemoryManager 里的短期记忆，一份是 Agent 真正发给模型的会话历史。问题是，只压缩前者并不会减少请求 Token。后来我删除了这份额外的消息副本，让每个 Agent 只维护自己的 conversationHistory，并在每次调用模型前直接统计和压缩它。

自动压缩有两条路径。实验开关开启时，系统会在阈值前为每份 conversationHistory 异步维护增量 Session Memory；真正达到阈值后优先使用已有摘要并保留最近原始消息。如果摘要未就绪、边界已经失效或者压缩后仍然超阈值，就回退到完整对话摘要。手动执行 `/compact` 始终走稳定的完整摘要路径并保留最近一轮。切分点只落在 user message 边界，避免拆开 assistant tool call 和后续 tool result。

这个方案解决了“压错对象”“不同模式短期状态串写”和“破坏工具调用边界”三个问题。原始消息由 ConversationLedger 只追加地保存到会话记录文件，因此压缩只改变下一轮发给模型的内容，不会改写已保存的记录。下一步还可以加入预计算摘要的新鲜度判断和按相关性选择性清理工具结果。

## 第二大题：实习相关

### 2.1 分片上传的指标怎么测出来的

这个指标我需要先澄清一下。项目现有的性能测试主要覆盖分片状态查询，不能直接证明 1GB 文件的端到端上传耗时从 15 秒降到了 3 秒。项目中前端按 5MB 分片，单文件最多使用 4 个 worker 并发上传；服务端使用 Redis Bitmap 管理分片状态，并结合数据库记录和 MinIO 对象检查保证幂等；获取已上传分片时会一次读取整张 Bitmap，再在本地解析。

项目里现有的性能测试，测的是分片状态查询的优化效果。它假设 Redis 单次往返是 3ms，对 5GB、约 1000 个分片的场景做模拟计算，比较“逐片查询 Redis”和“一次读取整张 Bitmap”的耗时。这个测试能证明 Bitmap 批量读取减少了 Redis 网络往返，但它不是 1GB 文件的端到端上传测试。

端到端测试时，我会固定客户端和 MinIO 所在网络、机器配置、文件内容、分片大小、并发数和连接预热条件，并明确测试是否包含文件 MD5 计算和服务端合并时间。我使用同一个 1GB 文件，优化前后分别预热，再各执行多轮测试，记录 P50、P95 和失败率。计时范围从客户端开始上传到 MinIO 合并完成，同时分别记录 MD5 计算、分片传输、Redis 状态查询和 MinIO 合并耗时。

1GB 在 3 秒内传完，相当于约 333MB/s，也就是约 2.7Gbps 的有效吞吐，因此测试环境必须是本机、同机房高速内网，或者存在部分分片已经上传过、可以直接跳过的情况。如果没有保存这组端到端测试的环境信息和原始日志，我会把项目成果表述为：

“基于 Redis Bitmap 将已上传分片状态查询由 N 次 Redis 往返优化为 1 次批量读取，并结合 MinIO 和数据库校验实现分片幂等和断点续传；前端采用 5MB 分片、单文件 4 并发上传。”

### 2.2 实习中如何用 AI 提效

我在实习中主要从三个层面用 AI 提效。

- **代码库理解和方案调研**：面对陌生项目时，我会先让 AI 帮我定位调用链、配置入口和可能受影响的模块，再回到真实代码逐个验证。比如排查分片上传问题，我会让 AI 先整理“前端切片、上传接口、Redis Bitmap、MinIO 合并”的完整处理过程，但最终结论必须以代码、日志和实际请求结果为准。
- **小步实现**：需求开始前，先明确输入输出、异常场景、验收标准和不能改动的边界，再让 AI 生成局部代码、测试样例或重构建议。每次只处理一个可验证的小改动，避免一次生成 Controller、Service、DAO 一整套代码之后，很难判断哪里出了问题。
- **测试和排障**：AI 很适合补充边界用例、解释异常堆栈、对比不同方案和生成排查清单，但我不会把它给出的“可能原因”直接当结论，而是通过日志、断点、单元测试、集成测试和压测逐个排除。

我最大的心得是，AI 提效的关键不只是把 Prompt 写长，而是把任务拆成上下文明确、验收标准明确、结果可以验证的小步骤。AI 负责加速搜索、生成和对比，我负责业务判断、风险控制和最终验收。另外，公司的源码、用户数据、密钥和生产日志，不能未经脱敏直接上传到不受控的模型服务。

### 2.3 如何保证 AI 输出内容的质量

保证 AI 输出质量，我会从五个环节入手。

- **输入质量**：给 AI 明确的任务目标、技术栈、代码约束、输入输出和验收条件，并提供必要的上下文，避免让模型自己补全业务规则。
- **证据约束**：让 AI 标明结论来自哪段代码、哪份接口文档或哪条日志。涉及版本、API 行为和业务数据时，回到一手来源核对，不能只相信模型“听起来合理”的解释。
- **人工 Review**：重点看业务逻辑、并发安全、异常分支、事务边界、权限校验、敏感信息和资源释放。语法正确不等于业务正确，更不等于生产安全。
- **自动化验证**：运行编译、静态检查、单元测试、集成测试和必要的性能测试。AI 也可以辅助生成测试，但测试断言必须由我根据需求确定，不能让 AI 同时定义实现和正确答案。
- **分级放权**：写注释、生成样板代码这类低风险操作可以自动化；涉及资金、删除数据、权限、生产发布的高风险操作，必须保留人工审批和回滚能力。

我的原则是，不直接相信 AI 的输出，只相信经过代码、测试和运行结果验证后的输出。

## 第三大题：PaiCLI 相关

### 3.1 压缩成摘要后，原始上下文还需要吗

原始上下文仍然有价值，因为摘要属于有损压缩，审计、追溯和恢复细节时可能需要原文。

PaiCLI 当前压缩的是 Agent 实际发送给模型的会话历史。较早的消息被摘要替换，最近几轮保留原文，后续请求只发送“摘要加最近消息”。被替换的原始消息目前没有自动持久化到数据库，`/export` 导出的也是压缩后重建的会话历史，拿不到压缩前的完整归档。

如果做生产级演进，我会把原始消息作为审计日志追加存储，摘要只用在发给模型的上下文里；再提供按会话、时间和关键词回查原文的工具。这样才能同时兼顾 Token 成本和可追溯性。

### 3.2 用户一个月前说喜欢吃辣，一周前又说不能吃辣，现在怎么判断

不能简单地用“最新记忆覆盖旧记忆”。“喜欢吃辣”描述的是长期偏好，“不能吃辣”可能是健康约束或临时状态，两者的类型、有效期和风险都不同。

更合理的做法是给记忆增加主题、类型、来源、时间、有效期和置信度。例如把第一条记为“偏好：喜欢辣”，第二条记为“约束：当前不能吃辣”。在推荐食物时，安全约束优先于口味偏好，所以先按“不能吃辣”处理；如果业务场景允许，再追问用户这是暂时忌口还是长期变化。确认是永久变化后，才把旧偏好标记为失效或降低权重。

PaiCLI 当前会把用户明确要求保存的稳定事实写入本地 JSON 文件，通过关键词匹配进行检索，支持新增、查询和删除。下一步我会补充同主题冲突检测、有效期管理和记忆类型划分，让长期偏好与临时约束能够分别管理。

### 3.3 记忆存储在向量数据库里，怎么更新已有记忆

先纠正问题的前提。PaiCLI 当前的长期记忆并不在向量数据库里，而是持久化到本地的一个 JSON 文件，检索方式主要是关键词匹配。完全相同的内容会去重，但没有通用的 update/upsert 接口，需要修改时，目前更接近于删除旧记忆再保存新记忆。

对于通用的向量记忆系统，我不会仅根据相似度找到最近的一条向量后直接覆盖，因为语义相似不等于同一个事实。我会根据用户、实体和属性生成稳定的业务键，例如 `(userId, dietary_constraint)`；写入时先按业务键查询当前有效版本，再根据新信息执行新增、合并、覆盖或失效。文本发生变化后重新生成 Embedding，新旧版本保留 version、validFrom、validTo 和 source 字段，向量库负责召回，关系库或文档库负责事实状态和审计。

也就是说，向量相似度适合找候选，稳定 ID 和版本字段才适合决定更新谁。

### 3.4 上下文压缩会不会丢失关键信息

会，这是摘要压缩的固有风险。PaiCLI 当前通过两个手段降低风险，一是只压缩较早的历史，保留最近几轮原文；二是只在 user message 边界切分，避免破坏 tool call 和 tool result 的对应关系。摘要 Prompt 会要求保留用户目标、已经完成的关键操作、已有结论和未完成事项。

当前实现仍然可能丢失精确金额、日期、文件名和错误码等细节，而且没有自动回查被压缩原文的能力。因此，上下文压缩只能降低信息丢失风险，不能彻底消除风险。

生产级方案通常把信息分成三类分别处理：

- 对话性内容允许摘要
- 金额、订单号、权限和状态等关键事实进入结构化状态
- 完整原文进入可审计存储

这样即使摘要遗漏，关键业务事实也不依赖摘要恢复。

### 3.5 用户购买商品花了 500 元，压缩后把 500 元丢失了怎么办

我的处理原则是不让订单金额只存在对话摘要里。订单金额应该以订单系统或支付系统为事实源，Agent 在需要时通过工具按订单号查询，摘要只保存“用户在咨询某订单”这样的上下文。

如果场景里暂时只有对话数据，可以在压缩前抽取金额、订单号、日期和状态等结构化事实（typed facts），写入结构化会话状态；摘要完成后再做一致性校验。发现关键事实缺失时，可以重新压缩，或者把结构化事实单独注入模型。不过正则只能覆盖格式明确的数字，处理不了“半价”“五百左右”“用了优惠券后”这类复杂语义，所以不能把正则当最终保障。

PaiCLI 当前还没有实现“金额实体抽取加压缩后校验”，这是我下一步会补充的能力。

### 3.6 如何定义哪些内容属于重要信息

我会从四个维度判断。

- **业务影响**：金额、订单状态、权限、用户确认、任务约束和外部系统返回结果，一旦丢失会改变后续动作。
- **不可恢复性**：能随时从数据库重新查询的数据，可以不全部塞进摘要；用户只说过一次、外部系统不再提供的信息，需要更谨慎地保留。
- **时间属性**：长期稳定偏好、当前临时状态和已经过期的信息，不能混为一类。
- **用户意图**：用户明确说“记住”“以后都按这个来”的信息，优先级更高。

PaiCLI 当前也是只有用户明确要求保存时，才会写入长期记忆，不会自动把每句话都变成永久记忆。工程上不能只靠一句 Prompt 让模型自由判断，更稳妥的做法是“摘要 + 结构化状态 + 原始审计日志”的分层设计，并针对金额、权限、状态转换等高风险字段做规则校验。

### 3.7 API 超时和报错怎么解决

先分类，再决定是否重试。连接超时、读超时、服务端 5xx、429 限流、参数 4xx、上下文超限和业务拒绝不是一类问题，处理方式也不同：

- 连接失败、偶发网络错误和部分 5xx，可以做有限次数重试，并使用指数退避加随机抖动
- 429 要读取服务端返回的 Retry-After，并配合客户端限流和排队
- 400、401、403 这类确定性错误不应该盲目重试，而是修正参数、密钥或权限
- 上下文超限要触发压缩、裁剪工具结果，或者切换更大窗口的模型

重试还必须考虑幂等性。纯聊天请求重复发送可能产生两份答案，调用退款、发消息、写数据库等工具重复执行更危险，所以要给请求和工具调用增加 requestId、幂等键和状态记录。超过重试上限后，再做熔断、模型降级或友好提示，同时保留 traceId、耗时、状态码、模型、Token 和错误阶段，方便定位。

目前 PaiCLI 的不同模型客户端已经配置了连接、读写和整体调用超时，但还没有统一的重试与熔断框架；派聪明的部分 Embedding 调用有固定间隔重试，聊天生成外层有超时控制。下一步我会把错误分类、指数退避、熔断、降级和幂等控制抽成统一的调用组件。

### 3.8 消耗 Token 过快怎么排查

第一步先判断是输入 Token 还是输出 Token 异常，并按请求、会话、用户、模型和 Agent 轮次记录。输入高通常来自上下文、工具 schema、工具返回结果、RAG 片段、图片和重复加载的 Skill；输出高通常来自模型回答过长、ReAct 循环过多或模型反复自我修正。

第二步拆解 Prompt 构成。PaiCLI 已经能够区分 system、user、assistant、tool 和 image 等内容，排查时要看是哪一块突然上涨。尤其要关注四个点：

- 历史压缩是否真的作用于发给模型的会话历史
- 工具返回是否把整份文件或整页网页反复带回
- 模型是否在多轮 ReAct 中重复读取同一内容
- Skill 是否只在需要时加载

第三步看调用次数。派聪明的 Agent 最多会进行多轮 ReAct 和多次工具调用，单次知识检索结果又会携带若干文本片段。即使每次 Prompt 不算特别长，循环次数乘起来也可能迅速放大 Token。需要统计每个问题调用了几次模型、几次检索、每段检索文本多长，只看最后一次请求发现不了这种放大。

第四步是针对性优化：

- 对历史做真实压缩
- 限制检索 topK 和单段长度
- 对工具输出先做结构化提取，再送回模型上下文
- 精简稳定的 system prompt
- 设置最大 Agent 轮次和单会话 Token 预算
- 对高频、确定性 FAQ 用缓存或规则直接返回

最后才是做 Dashboard 和告警。没有前面的分类埋点，只有总 Token 曲线也很难定位根因。

### 3.9 Skill 的渐进式披露机制

渐进式披露的核心是按需加载，先给模型看轻量索引，命中任务后再加载完整 Skill，需要更深的信息时，再读取 Skill 引用的脚本、模板或参考资料，避免启动时把所有内容都塞进 system prompt。

PaiCLI 当前的第一层是 Skill 索引。启动时会扫描内置、用户级和项目级三个来源，把启用 Skill 的名称和描述放入 system prompt。这里的“三个来源”是覆盖优先级，不是渐进式披露的三个阶段。索引最多保留 20 个 Skill，总长度最多约 4096 个字符。

第二层是完整 Skill 内容。当模型发现某个 Skill 的描述与当前任务匹配时，调用加载 Skill 的工具。完整的 SKILL.md 正文不会永久追加到 system prompt，而是写入一个 Skill 上下文缓冲区，在下一轮 user message 前注入，并且一次性消费。单个 Skill 正文最多注入约 5KB，缓冲区最多同时保留 3 个 Skill。

第三层是 Skill 引用的资源。Skill 正文只负责告诉 Agent 工作流和需要读取什么；真正用到某个模板、脚本或参考文件时再按需读取。这一层靠的是 Skill 编写规范和 Agent 的执行策略，不会把整个 Skill 目录一次性加载。

内置、用户级和项目级三个来源在注册阶段都会被扫描，真正按需加载的是完整 Skill 内容及其后续资源。

## 第四大题：场景题

### 4.1 智能客服 Agent 怎么设计

我会从请求入口、决策层、知识与工具层、状态层、安全层和评测层六个部分设计。

请求进来后，先做身份认证、租户隔离、敏感信息脱敏和意图识别。意图识别之后按类型分流：

- 高频且答案确定的 FAQ，由规则或缓存直接处理
- 知识咨询进入 RAG
- 查订单、改地址、退款等业务操作进入工具调用（Tool Calling）
- 投诉、法律风险和模型无法确认的情况转人工

RAG 的检索过程不能只追求“搜到了”，还要考虑文档解析、切片、混合召回、重排、权限过滤、引用来源和知识版本。模型只能基于有权限的证据回答，证据不足时应明确说不知道或追问，不能补写不存在的政策。

工具调用层要区分只读和写操作。查询订单可以直接调用；退款、取消订单、修改地址等写操作需要参数校验、幂等键、权限检查和必要的二次确认。多轮对话中，订单号、当前流程节点和已确认参数应进入结构化会话状态，不能完全依赖自然语言历史。

人工转接不能只依赖模型自报一个“置信度”。可以综合检索得分、是否有引用、规则命中、工具执行状态、重复追问次数、情绪和风险标签决定是否转人工。转接时要把对话摘要、已确认信息、证据和失败原因一起交给人工，避免用户重新描述一遍。

最后建立离线和在线评测。离线看检索 Recall@K、答案正确率、引用一致性、工具调用成功率和越权率；在线看首 Token 延迟、总响应时间、转人工率、一次解决率、用户满意度、成本和投诉率。

派聪明目前已经实现了其中的知识问答部分。知识检索被封装成 Agent 可以调用的检索工具，Agent 可以进行多轮工具调用并返回引用，也支持流式响应。订单、退款等业务工具、统一置信度评估、人工转接和完整评测体系，是我下一步会补充的部分。

### 4.2 电商大促流量尖刺怎么解决

第一层是入口保护。API 网关做鉴权、单用户和租户限流、全局并发限制、黑名单和排队提示。对于流式对话，不能简单把所有同步请求扔进 Kafka 后让用户一直等待；更合理的是做准入控制（admission control），超过模型并发或 Token 预算时，明确排队、降级或快速失败。消息队列更适合知识库解析、质检、会话总结和通知等异步任务。

第二层是减少进入大模型的请求。确定性 FAQ 走规则或经过审核的缓存，订单类问题优先调用业务接口，只有需要自然语言理解和生成时才调用模型。缓存要包含知识版本、租户和权限维度，不能把一个用户的订单答案缓存给另一个用户。不同用户的上下文和数据权限也不同，因此不会把多个用户的问题随意合并成一次模型请求。

第三层是保护大模型和下游服务。按 provider、模型和租户设置请求并发、每分钟 Token 上限和每日预算。对 429 和 5xx 做分类重试，设置超时、熔断、降级模型和最大 Agent 轮次。订单、库存等下游服务也要有独立的隔离舱（bulkhead），不能因为 Agent 流量把核心交易系统拖垮。

第四层是弹性扩容。Agent 服务尽量无状态，会话状态放 Redis 或持久化存储，根据活动连接数、排队长度、请求延迟和 Token/s 扩容，而不只是看 CPU。大促前通过压测估算容量并提前扩容，因为等 K8s 的水平自动扩缩容（HPA）看到 CPU 升高再拉起实例，可能已经来不及。

第五层是可观测性。监控 QPS、活动的服务端推送（SSE）连接数、首 Token 延迟、P95 总耗时、模型 429/5xx、队列长度、Token/s、缓存命中率、工具失败率和单请求成本，并准备限流、降级和模型切换预案。

### 4.3 生产中 CPU 100% 怎么排查

先确认是单核打满还是整机所有 CPU 打满，同时看 user、system、iowait、load average 和容器 CPU throttling，避免只看到一个 100% 就直接判断是 Java 死循环。

如果是 Java 进程，先用 `top` 或 `pidstat` 找到高 CPU 的 PID，再用 `top -Hp PID` 找到高 CPU 线程的十进制 TID，转换成十六进制后，在 `jstack` 中根据 `nid` 定位线程。不要只抓一次堆栈，应该间隔几秒抓三次。如果同一个线程一直停在相同业务栈，才更能说明是热点循环或计算瓶颈。

拿到堆栈后按特征分情况处理：

- 线程主要在 GC，就用 `jstat`、GC 日志或 JFR 判断是不是对象分配过快、堆太小或内存泄漏
- 热点在正则、JSON 解析、序列化、文本切片或 Embedding 前处理，就用 async-profiler 或 JFR 看 CPU 火焰图
- 大量线程处于 BLOCKED 状态，要排查锁竞争和死锁
- system CPU 很高，还要看网络、文件和内核调用

线上处理顺序应该是先止损再深挖：限流、摘除异常实例、扩容或回滚到上一版本，同时保留现场数据，然后再分析堆栈、火焰图、GC 和最近变更。不要一上来重启，否则最关键的现场可能丢失。

AI Agent 场景要特别关注长文本分词、RAG 文档解析、JSON/SSE 增量拼接、死循环式 ReAct 和无上限并行工具调用。SSE 连接“等待模型返回”通常主要占连接和内存，并不会天然导致 CPU 100%；真正要看的是忙轮询、重复解析、无限重试或复杂后处理。

### 4.4 点赞系统怎么设计

先明确需求，比如是否只支持点赞和取消点赞、是否需要查看点赞用户列表、计数能否接受最终一致、要不要防刷，以及峰值 QPS 和数据量是多少。不同规模下，方案复杂度完全不同。

核心数据模型可以设计一张点赞关系表，唯一键是 `(user_id, target_type, target_id)`，状态表示已点赞或已取消；计数单独维护。唯一键保证重复请求不会产生多条关系，接口再配合 requestId 或业务幂等键。中小规模场景直接使用数据库唯一索引和事务就足够，不需要为了“高并发”一上来堆很多中间件。

高并发场景可以把 Redis 作为实时状态和计数层，但“用户集合变更”和“计数加减”必须通过 Lua 脚本原子执行，不能分别执行 `SADD` 和 `INCR`，否则部分失败会造成计数不一致。只有 `SADD` 真正新增成功时计数才加一，只有 `SREM` 真正删除成功时计数才减一，并防止计数变成负数。

持久化方面，我会通过事务消息、发件箱模式（Outbox）或可靠事件流，把状态变化异步写入数据库，消费端根据事件 ID 幂等处理；定期使用点赞关系表或事件日志与 Redis 计数进行对账修正。读取时优先查 Redis，缓存失效时从数据库重建。

对于明星文章形成的热 Key，可以做本地短缓存、读副本、计数分片后汇总。点赞用户列表使用分页或时间游标，不能一次返回整个 Set。还要考虑用户限流、设备/IP 风控、机器刷赞、删除文章后的数据清理，以及点赞通知异步化。

这个系统的设计重点，是同时保证幂等、原子性、持久化、最终一致性和热点治理，单纯用 Redis 替代 MySQL 解决不了这些问题。
