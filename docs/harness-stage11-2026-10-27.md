# 阶段十一：L05 顺序回归调查与工具上下文一致性修复

本轮排除了“L05 因上下文压缩丢失顺序”的解释，修复了真实执行中的工具声明不一致问题，并纠正评分盲点。**尚未实现 L05 稳定通过：本轮修改前 1/1、修改后 1/2 满足完整验收。** 失败样本保留，不宣称成功率、成本或稳定速度改善。

## 1. 原始要求及历史执行顺序

原 L05 用户原话未修改：

> 验证工具参数校验：先故意调用一次 read_file 并提供空 JSON 对象 {} 作为参数；看到参数错误后，再用正确参数读取 alpha.txt。最后只回答整数值。

因此必须验证指定错误、观察错误后的恢复，以及正确结果；不是只要最后回答 17。

| 阶段十样本 | 实际工具事件顺序 | 旧评分 | 新评分 |
| --- | --- | --- | --- |
| 修改前 | read_file 失败（记录的 path 为空）→ alpha.txt 成功 → 17 | 通过 | 证据不足：未保存失败调用的完整参数，不能证明是空对象 |
| 修改后 | alpha.txt 成功 → read_file 失败（path 为空）→ alpha.txt 再成功 → 17 | 通过 | 失败：在指定错误发生前就执行了成功读取 |

修改后日志时间为 2026-10-27 13:57:15.587–13:57:20.649。模型先在 reasoning 中表示要提交 `{}`，实际却请求 alpha.txt；下一轮明确承认先读成功，随后补错误、再读文件。顺序来自实际模型响应和工具执行记录，没有证据表明 Kernel 调换了调用。相关脱敏日志摘录与两份历史重判保存在结果目录。

历史 Trace：修改前 `116811ca17ac9a6481a45604ad59967f`；修改后 `0ac9a3bba79323041ffd0f20a58d926f`。历史本地记录与云端未保存完整请求/参数，不能从空 path 推断参数必然为 `{}`，也不能把模型 reasoning 当作实际执行证据。此前“补充顺序后 12/12→11/12”的摘要不等于已经验证了所有指定错误参数；严格口径下，历史修改前 L05 需要标为证据不足。

## 2. 为什么不是压缩器导致

- L05 每次新建 Agent，只有一个外部 user turn；完整摘要保留至少三个最近 turn，此时提前返回，不会请求摘要模型。
- 上下文约三千估算 Token，远低于该配置约 96.7 万的触发阈值；本轮保存的所有请求仍包含完整原任务，没有压缩摘要标记。
- 历史消息数按 2/4/6/8 增长，与普通工具反馈循环一致。阶段十改动的摘要生成逻辑未进入 L05 调用路径。
- 本轮 `ConversationHistoryCompactor.java`、`AgentExecutionKernel.java` 的阶段前后 SHA 相同，保留上一阶段有效改动；详见 source-before/after.json。

所以没有修改压缩算法，也没有声称找到了历史随机顺序违规的唯一成因。历史完整模型输入不可恢复是明确的证据缺口。

## 3. 受控基线暴露的真实 Harness 问题与生产修复

一次受控基线保存了实际客户端 messages、tools、响应和工具执行。请求只开放 `read_file`，system 却保留完整通用工具清单。模型在参数错误后依次尝试 `glob_files`、`list_dir`，均被现有权限策略以 `TOOL_NOT_ADVERTISED` 拒绝，然后才正确读取。提示词和可执行能力不一致有直接运行证据，但不能据此断言它必然导致了历史的早读行为。

生产改动：

| 文件 | 真实行为变化 |
| --- | --- |
| `src/main/java/com/paicli/agent/Agent.java` | ReAct 在 TurnToolPolicy 得出实际暴露工具后，更新真实 conversationHistory 的 system 消息；会话账本同步记录。预算收尾刷新为空工具，不重复加载外部上下文。 |
| `src/main/java/com/paicli/prompt/PromptAssembler.java` | 纯函数移除宽泛静态工具清单，写入本次请求实际工具集合；保留其他提示词层次，无第二套影子上下文。 |
| `src/main/resources/prompts/base.md` | 明确控制依赖应在看到前置实际结果后再决策；参数校验练习应使用指定参数对象，不能用后补错误抵消先前操作。此项是模型指导，不能保证确定性执行。 |

实际链路：`Agent.chat → TurnToolPolicy.expose → updateSystemPromptForTools → conversationHistory/ledger → AgentExecutionKernel 模型请求 → 原有工具权限和参数校验 → 工具结果进入下一轮`。没有放开工具权限、把路径字符串强改成空参数、伪造失败或插入专为 L05 的运行时状态机。

目前动态工具清单迁移只覆盖 ReAct，不能声称 Plan/Team 已迁移。基础控制依赖指导由共享资源复用。最后一次纯函数整理避免每轮重复加载外部上下文；针对性测试验证每个 user turn 只加载一次。独立离线重建证明最终函数渲染与两次修改后真实运行的全部六个请求 system 字节相同（prompt-equivalence.json），没有因此额外调用模型。耗时仅代表已执行批次，不推算最终整理的性能收益。

## 4. 评分盲点及修复

旧评分仅检查最终 17、至少两个工具调用、至少一次失败、出现 alpha.txt，未关联故障、参数、后续决策及恢复结果，因此历史违规和本轮错误参数都可能通过。

`OrderedRecoveryJudge` 与原运行器合用，在原条件之上要求：首个实际事件是指定工具以空参数对象产生失败；恢复发生在更晚的模型决策轮，该请求确实包含对应 call ID 和实际错误内容；恢复工具及参数正确、成功结果含精确 fixture 行 `ALPHA=17`，最终仍为 17。同批并发调用不能冒充“看到错误后”；失败/错误值恢复、无关错误、`{"path":"{}"}` 都不能算指定参数错误。缺少历史参数时返回 `INSUFFICIENT_EVIDENCE`，不猜测。

用例只增加结构化 orderedRecovery 验收字段，12 条原 prompt 均未改。历史原用例、旧评分、输出均保留；新报告版本为 `ordered-recovery-v2`。评分器代码属于生产评测入口，不替代上述 Agent 执行修复。

重判入口（无需模型或云端）：

```powershell
java -cp $cp com.paicli.eval.live.LiveHarnessMain --rejudge-l05 before.json after.json new-output.json
```

输出不能覆盖已有文件。三个 `rejudged-*-final*.json` 保存了本轮实际重判，复核时使用新的输出路径。可选 `-CaptureContext` 仅允许顺序单独运行 L05，在本地保存实际上下文，不修改云端默认脱敏规则。
