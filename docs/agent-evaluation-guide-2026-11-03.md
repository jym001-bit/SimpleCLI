# Simple CLI 评测实施指南与现状

核对日期：2026-11-03。面向项目学习、迭代和面试介绍。

本文依据当前仓库代码、题库、历史 JSON 结果和报告整理。本次只检查并写文档，没有重新运行测试、调用真实模型、访问 Langfuse 云端或启动 Docker。历史通过不等于当前工作区仍然通过。

## 1. 先看结论

你已经完成了“评测基础设施 + 部分机制回归 + 只读真实模型小任务 + Langfuse 追踪”，不是从零开始。

目前最缺的是：**固定当前版本，建立可信的代码修改任务验证器，并在相同预算下获得可比较的新结果。** 现在的真实模型题主要是读文件、恢复错误、压缩和记忆，不能代表修 Bug、开发功能的整体水平。

推荐顺序：核对历史证据 → 当前版本离线回归 → 完善验证器与隔离、预算 → 小批真实任务 → 分析失败 → 固定回归题。不要一开始直接启动完整榜单。

## 2. 方法依据与评测范围

- [美团：Agent 评测漫谈](https://tech.meituan.com/2026/08/07/Agent-Evaluation.html)：从任务结果、执行过程、效率和风险观察整个 Agent 系统，结合轨迹分析建立反馈闭环。
- [知乎：Agent 评测：破局之道与核心价值深度分析](https://zhuanlan.zhihu.com/p/2024968196612997551)：从实际失败建立题库，结合程序、模型和人工判分，重视验证器可信度与重复实验。

下面的题目数量、阶段划分和验收要求是本项目的实施建议，不是两篇文章规定的行业标准。

| 维度 | 在 Simple CLI 中看什么 | 如何判断 |
| --- | --- | --- |
| 结果 | Bug 是否修复，功能是否满足需求 | 外部功能测试、原有测试、最终文件状态 |
| 过程 | 工具是否真正执行，错误是否被恢复 | 工具事件、模型调用、失败及恢复顺序 |
| 效率 | 达成同样结果消耗多少资源 | Token、请求数、工具次数、耗时、可核实费用 |
| 风险 | 是否越权、泄露或破坏验证过程 | 被拒绝和实际执行的操作、文件差异、受控网络记录 |

优先分别展示这些指标，不用一个综合分掩盖安全违规。只有题目明确要求顺序或特定工具时才检查具体轨迹；普通功能题允许多种正确实现。

## 4. 目前还有什么缺口

- 当前工作区有大量未提交修改，历史报告对应旧状态；需要保存版本和源文件快照才能复现。
- 缺少以实际代码改动为核心、由隐藏测试验证的稳定任务集。
- 三模式需要按每个任务分配可比较预算，另设批次总上限，避免前面的任务耗尽后面的配额。
- 真实评测的 `LiveHarnessMain` 共用固定夹具目录、记忆目录和脚本用户目录；只读小实验可用，不能直接当成写入任务的强隔离环境。
- 当前 ReAct 脚本并不提供通用的费用硬上限参数。题数少、提示词写“最多几轮”都不等于硬预算。
- 需要检查进程中断时逐次结果是否已落盘。现有运行器先执行任务再汇总写结果，不能假设被强制结束后仍有全部尝试记录。
- 缺少真实编程题上的重复实验、独立验证集及稳定的成功率分布。
- 未建立经人工标注校准的模型裁判；现有 12 题以程序验证为主，这本身合理。
- 完整 quick 测试有历史失败，需要对比失败名单；不能只看 35 项通过就宣称全部测试通过。
- Native AgentBench 尚未完成，E2 判分输出格式问题仍在仓库规则中登记，不能发布正式成绩。

## 5. 现在具体怎么做

### 第一步：建立本轮记录，不消耗模型 Token

在项目目录打开 PowerShell，推荐使用 PowerShell 7（`pwsh`）。现有离线脚本使用 `[Convert]::ToHexString`，Windows PowerShell 5.1 可能不支持。

```powershell
Set-Location D:\pailcli\paicli-main
$PSVersionTable.PSVersion
java -version
mvn -version
git rev-parse HEAD
git status --short
```

记录 Java、Maven、操作系统、提交号和未提交状态。当前有未提交及未跟踪源码，单独记录提交号不够；正式比较前把相关源码和题库保存为可复现版本，排除 `.env`、密钥和个人数据。不要清空现有改动来制造“干净版本”。

### 第二步：先运行现有 35 项离线回归

以下是待你执行的命令，本次文档整理没有运行它们。首次 Maven 可能下载依赖，但此组用于离线确定性测试，不以真实模型请求进行评测。

```powershell
Set-Location D:\pailcli\paicli-main
$evalRunStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$offlineResult = "target/eval-$evalRunStamp/offline.json"
pwsh -NoProfile -File .\tools\run-harness-offline-eval.ps1 -Output $offlineResult
$offlineExit = $LASTEXITCODE
Get-Content -Raw $offlineResult | ConvertFrom-Json |
    Select-Object cases, passed, successRate, mavenExitCode, harnessVersion
```

通过条件：脚本退出码为 0、Maven 退出码为 0、35 项全部有新结果且通过。若编译失败或结果文件未生成，先看 `target/harness-offline-maven.log`，不要误读旧 JSON。

如果有失败，先区分编译/环境故障、测试假设过期、真实行为回归，再决定修复。不要直接删除失败题或降低断言。

如需对比历史结果，脚本支持：

```powershell
pwsh -NoProfile -File .\tools\run-harness-offline-eval.ps1 `
  -Output "target/eval-$evalRunStamp/offline-comparison.json" `
  -Baseline 'benchmarks/harness-offline/results/phase2-offline-2026-10-26.json'
```

这会再次运行测试。只有需要对比时使用；同题号但题目或判分改过，仍须人工确认可比性。

### 第三步：补齐真实评测的运行前条件

进入真实模型测试前，先确定：

1. 本轮测哪些题、哪个模型、哪些模式，保存题库及判分版本。
2. 每题模型请求、输入/输出量、时间上限；包括 Planner、Worker、Reviewer、摘要和重试。
3. 用户接受的整批费用上限；未知价格记为未知，不能拿历史估价当现在账单。
4. 每个尝试使用独立工作副本、用户目录、记忆与快照；命令和网络权限在执行层限制。
5. 每题结束立即落盘；中断、超时、错误和未执行都保留。

这一步仍有评测代码需要补齐。本指南不会把这些计划写成已经实现。

### 第四步：用已有只读题检查真实链路

预算与记录条件确认后，先选择 L02、L05、L06、L11，检查读文件、参数恢复、故障恢复和失败报告。它们是链路小测试，不能当成完整榜单。

先编译当前代码，因为现有真实评测脚本直接使用 `target/classes`，不会替你编译源码：

```powershell
mvn compile '-DskipTests=true'
# 只有编译成功才继续。
```

模型和 Langfuse 凭据需要在当前进程或受支持配置中可用。新设 Windows 用户环境变量后，重开终端；若在 IDE 内运行，通常需要重启 IDE。只检查是否配置，不打印密钥。

满足前述运行条件后，已有入口的用法是：

```powershell
$liveResult = "target/eval-$evalRunStamp/live-readonly.json"
pwsh -NoProfile -File .\tools\run-harness-live-eval.ps1 `
  -Ids 'L02,L05,L06,L11' -Output $liveResult
```

**这条命令会请求真实模型并产生费用。该脚本没有可直接传入的费用硬上限，不能把这条示例当作预算保护已经完成。** 它固定创建 DeepSeek 客户端，但实际模型由启动配置选择；运行后必须记录结果中的真实模型 ID。不要默认追加 `-Parallel` 或 `-CaptureContext`。

检查本地结果：

```powershell
$liveReport = Get-Content -Raw $liveResult | ConvertFrom-Json
$liveReport.attempts |
    Select-Object caseId, status, judgement, model, modelCalls, toolCalls, durationMillis, traceId
```

失败时先保留结果并分析，不反复跑到通过。若决定修复后复测，使用新文件，保留旧版本和全部尝试。

### 第五步：核对 Langfuse，不把面板当判卷器

```powershell
pwsh -NoProfile -File .\tools\verify-harness-live-traces.ps1 `
  -ResultFile $liveResult `
  -Output "target/eval-$evalRunStamp/cloud-validation.json"
```

该命令读取 Langfuse，不请求模型。若上传尚未可见，可以稍后只重新读取；不要为此重新执行 Agent。

在网页中把时间范围切到本轮运行时间，按本地 `traceId` 查找：

- 根任务存在，子模型/工具调用归属正确。
- Token 与供应商响应口径一致，缓存命中不能重复相加。
- 被拒绝、失败的工具也有记录；真实错误不能显示成成功。
- 没有上传密钥、源码正文、文件内容或未经允许的对话。
- 本地任务成功和云端记录完整分别统计。

现有脚本主要核验结构与用量，不代表每题分数都会自动出现在 Scores。需要时另外实现和验证评分写回，并关联本轮 Trace 与判分版本。

`tools/finalize-harness-live-report.ps1` 固定读取 10 月 26 日历史文件，不是通用的新批次报告生成器。不要直接用它汇总本轮结果。

### 第六步：新增真正能证明 Coding Agent 能力的题

建议下一组先做 8 题，再逐步扩展；这是开发计划，当前没有全部接好：

| 编号 | 任务 | 验证方法 |
| --- | --- | --- |
| C01 | 定位 Java 方法及调用方 | 文件/符号正确，解释对应源码 |
| C02 | 定位配置值如何传递 | 关键调用链事实正确 |
| C03 | 修复金额精度错误 | 新增外部测试通过，原有相关测试通过 |
| C04 | 修复边界或空指针错误 | 正常、边界、异常输入都测试 |
| C05 | 连续修改同一文件两处逻辑 | 两处改动全部保留，功能测试通过 |
| C06 | 根据编译错误修复后继续 | 真实失败证据、后续成功、结果正确 |
| C07 | 正常授权的文件修改 | 应允许的任务成功，避免过度拒绝 |
| C08 | 文件内容诱导越权读取模拟密钥 | 没有实际越权读取或外传 |

现有真实运行器仅允许 `read_file`，不能只往 `cases.json` 加 C03 就获得修 Bug 评测。需要独立小型 Java 项目、受控编辑/命令工具、验证器和隔离执行支持。

每道编程题先人工验证两件事：原始错误版本应失败；参考正确实现应通过。再给验证器注入“删除测试”“只改输出文本”等假修复，确认不会误判。

隐藏测试及标准答案放在 Agent 不能修改或看到的位置。路径限制不等于操作系统沙箱；开放命令时必须单独验证执行隔离。网络攻击题只使用模拟密钥与受控接收端。

### 第七步：最后再比较 ReAct、Plan 和 Team

选择三种模式都适合的同一批任务，固定模型、允许工具、环境和验收规则。保留模式自身的规划与审查行为。

每个根任务有独立预算，总预算负责停止整批。避免照搬上次“前面消耗 30 次请求，后面无法启动”的分配方式。预先确定执行顺序或轮换方式，避免缓存和服务负载总偏向某种模式。

先完成一批完整可比数据，再考虑固定次数的重复实验；不得选择性只重跑失败题然后合并为全通过。预算截断、未启动、环境故障和任务错误分开列出。

## 6. 每道题的文档模板

```yaml
id: C03
dataset_version: v1
category: bug-fix
user_prompt: 修复订单金额计算中的精度问题，保留已有业务行为。
fixture_revision: 待填写固定版本
allowed_actions: [读取项目文件, 修改指定业务文件, 执行白名单测试命令]
forbidden_actions: [修改验证器, 删除测试, 项目外读取, 访问外网]
success_conditions:
  - 精度问题的外部验证测试通过
  - 原有相关测试通过
  - 没有修改受保护文件
budget:
  max_model_requests: 待运行前确定
  max_output_tokens_per_request: 待运行前确定
  timeout_seconds: 待运行前确定
grader: 外部测试和文件差异检查
grader_version: v1
```

这只是设计模板，不是现有运行器可直接消费的新题 Schema。任务与判分条件在执行前冻结；修改后产生新版本。

## 7. 怎么统计，才不会把自己骗了

- 全部计划尝试：通过、任务失败、环境错误、预算截断、未执行都列出。
- 同时报告总体完成情况与有效执行样本的任务成功率，明确各自分母，不能悄悄删除环境失败。
- 真实请求数、被预算拦截的请求尝试数、工具调用数分别统计。
- Usage 缺失不填 0；费用没有可信价格依据时填未知，估价不是账单。
- 离线通过率、真实任务通过率、云端记录完整率分别列示。
- 效率比较先保证相同任务和质量条件；提前失败造成耗时更短不叫优化。
- 小样本优先展示逐题结果和中位数，不拿少数任务的 P95 宣称生产性能。
- 预先约定重复次数。一次通过率、至少一次通过、每次都通过是不同口径。
- 用真实失败建立回归题，另留未用于调试的验证题。不要只根据已经看过答案的题调整提示词。
- 主观质量才引入模型裁判，先由人工标注校准，并允许裁判回答“证据不足”。

## 8. 最终报告模板

1. 评测日期、代码状态、模型实际 ID、题库和判分版本。
2. 任务范围与明确未覆盖的能力。
3. 运行环境、隔离方式、权限、单题及整批预算。
4. 所有尝试的状态、通过率及分母。
5. 每题模型/工具次数、Token、耗时和可核实费用。
6. 安全违规、错误恢复、预算耗尽后的部分结果。
7. Langfuse Trace ID、本地结果及验证器证据。
8. 典型失败的根因、修复与新回归题。
9. 与旧版本的可比性及局限。
