# 技术学习页与视觉改版

仅在写技术学习笔记、重做长页或用户明确要求可视化时读取。

## 从读者的问题组织页面

先列出读者进入页面时最可能问的 2–4 个问题。对技术项目，通常是：它解决什么、一次真实请求怎么走、出现异常会怎样、哪些结论已有证据。以具体场景开头，再把场景中的步骤映射到类、工具和数据。原始日志、完整测试矩阵与提示词可留在附录；保留其事实和链接。

写法参考：一句话解释 → 一个具体例子 → 图或简短步骤 → 对应源码 → 结果与边界 → 可展开的原始记录。并非每篇都需要所有部分。用户反馈“太理论”时，先修正前两屏的阅读路径和可见内容，不要只在页尾加概念表。

## 标题与层级

- 页面标题用“主题 + 读者会查找的具体问题”，例如“PaiCLI Agent｜从提问到完成：执行、失败与取消”；保留项目名等搜索锚点。
- 主标题用平行的问句或动作，不堆“概述 / 总览 / 视角 / 口径”等抽象词。页面标题不要在正文重复一次。
- 长页先给核心图和简短状态，再给源码、验证表和历史记录。目录若被折叠块内的深层标题挤满，就改用更浅的标题或简短手工导航。
- 旧版长表若遮住主要内容，可移到“数据速查/附录”，但必须保留重要数值与限制。

## 图的选择与制作

| 要解释的问题 | 优先形式 | 图旁必须交代 |
| --- | --- | --- |
| 请求如何循环调用模型和工具 | 带回环箭头的流程图 | 一次具体请求、谁决定、谁执行 |
| 完成、预算、失败、取消有何区别 | 决策图或结果卡片 | 触发原因、系统动作、用户看到的结果 |
| 多阶段改造如何连起来 | 少量分组的时间线 | 阶段范围、已验证与未验证 |
| 模块职责和关系 | 组件/关系图 | 真实调用边界，不臆造数据流 |
| 耗时/成本趋势 | 图表 | 数据来源、样本和测量口径 |

优先使用运行时支持的 Notion 原生块；当图的关系无法清晰表达且工具支持文件上传时，可制作 PNG/SVG，先检查文字、箭头、对比度和移动端宽度，再上传并靠近对应解释插入。若工具只支持 Markdown 代码块，明确说明它是图的源码而非已渲染图片。不要用无数据的柱状图装饰页面。

## 写后读者验收

回读确认图片已成为稳定的 Notion 文件块或可用链接；页面首屏确实显示新标题和图；图旁有例子；旧事实与附件仍在。问自己：第一次读的人能否在一分钟内说出主流程和一种异常出口？若不能，优先删减抽象导语、调整顺序或改图，而不是继续加表格。
